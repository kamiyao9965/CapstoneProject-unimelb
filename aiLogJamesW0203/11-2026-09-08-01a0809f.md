**The key is to give configuration enough information.** Replacing prompts alone is insufficient, because prompts cannot reliably handle structural validation, identity uniqueness, and review decisions. The trade-offs among three directions are:

| Direction | Suitability for your goal |
|---|---|
| Put all differences only in prompts | Easy integration, but output structure and validation can become difficult to control |
| **Shared engine + declarative configuration + prompts** | **Best fit: supports zero-code integration within a defined scope** |
| Let the manifest support arbitrary scripts and expressions | Appears to be zero-code, but actually moves business code into configuration and increases maintenance costs |

“Declarative configuration” here means supplying rules and parameters the engine already understands, without writing programs in it.

I suggest using the following as the draft proposal.

**Problem to solve:** How can the project team run, compare, and review multiple insurance domains in one workspace, adding only configuration and prompts when introducing similar domains?

**Recommended structure:** Keep the existing directories, with one configuration package per domain:

```text
configs/
  private_health/
    manifest.json
    prompts/
      discovery.md
      patch.md
      extraction.md
    aliases.json          # 可选
  travel_insurance/
    manifest.json
    prompts/
      discovery.md
      patch.md
      extraction.md
    aliases.json
```

The manifest handles the domain identifier, display name, document types, product classifications, input/output paths, prompt references, supported capabilities, and policies such as consensus rounds and protected fields. Prompts handle domain knowledge and evidence interpretation. **The specific extraction fields are still produced by the discovery and review workflow; onboarding a domain does not require manually writing a full business schema.**

To achieve this goal, the most important step is to unify the following four boundaries:

1. **Unify the internal schema structure.**
   Health currently uses `hospital_categories` and `extras_services`, while Travel uses `coverage_categories`; classification fields also sit in different locations. Define a shared structure that turns these differences into classification sets in configuration. Integrate old schemas through explicit version migrations and retain existing approved versions.

2. **Replace domain-name conditions with general rules.**
   For example, “how many products per document,” “which fields must not be changed automatically,” and “which set a classification must belong to” should all be executed by the same validation code reading configuration. Do not add `if vertical == ...` when adding a domain.

3. **Discover configuration packages automatically.**
   UI, CLI, prompt loading, and contract loading use a unified entry point. A new directory is recognized when added, removing the current need to modify Python vertical and prompt lists.

4. **Distinguish document classification from product classification.**
