### [2026-10-12T03:16:13.222Z] Codex

**Your direction can work: one main workflow, with document links, prompts, schemas, and quality checks configured through the manifest.** Document-linking rules can be generalized; the schema representation still needs choosing. Details follow.

**1. `amends_document_ids` can be generalized, but grouping must use the complete relationship graph**

For example:

```json
[
  {"document_id": "pds_A", "amends_document_ids": []},
  {"document_id": "spds_B", "amends_document_ids": ["pds_A"]},
  {"document_id": "pds_C", "amends_document_ids": []}
]
```

This produces two extraction tasks:

| Input | Output |
|---|---|
| `pds_A + spds_B` | Extract products using base terms and amendments |
| `pds_C` | Extract independently, potentially outputting multiple products |

Your idea is right. However, `[]` specifically means “this document does not declare that it amends another document.” Although `pds_A` has `[]`, `spds_B` still links to it.

I recommend unified rules:

- Extract ordinary PDS documents independently when they have no links.
- SPDS/Update documents must explicitly link to base documents; unconfirmed links enter a pending-check state.
- Check that references exist and contain no cycles, and preserve every source document.
- Which products and fields an amendment affects is still determined from the source text.

Another existing behavior was found: **besides amendment links, Pet also merges base documents declaring the same `product_id`.** If the unified workflow should base relationships entirely on `amends_document_ids`, that behavior needs explicit adjustment. [Pet grouping implementation](https://github.com/kamiyao9965/CapstoneProject-unimelb/blob/24473a2a1bc562f1d39db8aaccbeba2a6e8f25ea/src/schema_application/product_families.py)

**2. The three schema representations mainly differ in “how objects inside lists are described”**

They all eventually compile into runtime JSON Schema. The difference is how much structural information the saved business schema provides.

Use the following limit field as an example:

```json
{"limits": [{"amount_aud": 1000, "period": "per_year"}]}
```

The following is simplified, omitting other metadata.

**Travel's current approach: mainly describe object contents in prose**

```json
{
  "name": "limits",
  "type": "list[object]",
  "description": "Each item contains amount_aud and period."
}
```

The compiler knows `limits` is a list of objects, but does not specify which fields each object must have or their types. The following contents may therefore also pass this layer of structural validation:

```json
{"limits": [{"amout_aud": "1000", "period": "sometimes"}]}
```

Misspelled field names, amounts changed to strings, and unexpected periods are all unrestricted by the internal contract. [Current compiler]( /Users/yangyajing/proj/CapstoneProject-unimelb/src/schema/contract.py:91)

**Health/Pet: use `item_fields` to list fields inside objects**

```json
{
  "name": "limits",
  "type": "list[object]",
  "item_fields": [
    {"name": "amount_aud", "type": "number", "required": false},
    {
      "name": "period",
      "type": "enum",
      "values": ["per_year", "per_claim"],
      "required": false
    }
  ]
}
```

The compiler can now check field names, amount types, and period enums.

It is easy to read and suits schema discovery. However, current `item_fields` mainly supports **string, number, boolean, and enum**, and cannot directly continue describing complex inner objects or arrays. [Pet field compiler](https://github.com/kamiyao9965/CapstoneProject-unimelb/blob/24473a2a1bc562f1d39db8aaccbeba2a6e8f25ea/src/schema/field_contract.py)

**Car: use `item_schema` to describe object structure directly**

```json
{
  "name": "limits",
  "type": "list[object]",
  "item_schema": {
    "type": "object",
    "properties": {
      "amount_aud": {"type": ["number", "null"]},
      "period": {
        "type": ["string", "null"],
        "enum": ["per_year", "per_claim", null]
      }
    },
    "required": ["amount_aud", "period"],
    "additionalProperties": false
  }
}
```

Here:

- `properties`: the fields and each one's type.
- `required`: fields must appear.
- `null`: explicitly represents unknown values when the source does not provide them.
- `additionalProperties: false`: rejects undeclared fields.

**“A field must appear” and “its value must be known” are different.** For example, the following unknown value remains valid:

```json
{"amount_aud": null, "period": null}
```

Car can also describe multilayer structures like this:

```json
{
  "benefit_name": "Example cover",
  "limit": {
    "amount_aud": 1000,
    "period": "per_year"
  }
}
```

It can reuse structures through local `$defs` too; remote and circular references are prohibited in the current implementation. [Car nested implementation](https://github.com/kamiyao9965/CapstoneProject-unimelb/blob/571fc65a849dcb708a98da605c0103685efcf251/src/schema/nested.py)

I used the actual compilation functions to validate this limit example locally:

| Content | Current Travel approach | Health/Pet | Car |
|---|---|---|---|
| Numeric amount, valid period | Pass | Pass | Pass |
| Amount is the string `"1000"` | Pass | Reject | Reject |
| Misspelled field name | Pass | Reject | Reject |
| Period is an invalid enum | Pass | Reject | Reject |
| Explicit unknown value `null` | Pass | Pass | Pass |

**I favor adopting Car's `item_schema` uniformly.** It is longer and costs more to maintain and include in model input, but expresses complex structures. Health/Pet syntax is simpler and suits shallow objects. Given the four verticals' existing complex limits, exceptions, and evidence structures, Car's expressiveness is the better fit.

All four verticals can use the same schema syntax while defining their own fields and business constraints. Some current Car implementation remains tied to the car-insurance review profile, so general capabilities need extracting when joining the shared workflow.

**3. Structural checks, evidence checks, and a judge without labelled ground truth are acceptable**

The integrated shared workflow can use:

```text
结构校验 → 业务与证据检查 → 独立 judge → 必要时人工复核
```

Structural validation checks types and fields; evidence checks inspect references, page numbers, and relationships; the judge assesses consistency of extracted content with the source. Judge pass rate should be treated as a quality-audit metric.

One integration requirement is crucial: **when Pet extracts from multiple documents, the judge must read the same document group.** Otherwise, an amount changed by an SPDS may not be found in the base PDS, causing a false judgment. The current Travel judge reads one PDF and requires an approved Canonical Schema, so this needs extending. [Existing judge entry point](/Users/yangyajing/proj/CapstoneProject-unimelb/src/evaluation/quality.py:83)

I support not merging the Health branch's new labelled-evaluation enhancements this time. Whether main's existing labelled module remains optional or is moved out still needs your choice; the shared workflow can be completely independent of it.

**4. A manifest is vertical configuration, and the document inventory can be part of it**

I agree with that definition. I recommend retaining the existing `documents` configuration structure and adding `inventory` within it:

```json
{
  "vertical": "pet_insurance",
  "prompts": {
    "extraction": "../../prompts/pet_insurance/extraction.md"
  },
  "documents": {
    "inventory": [
      {
        "document_id": "pds_A",
        "source_path": "data/pdf/pet_insurance/base.pdf",
        "document_role": "pds",
        "amends_document_ids": []
      },
      {
        "document_id": "spds_B",
        "source_path": "data/pdf/pet_insurance/update.pdf",
        "document_role": "spds",
        "amends_document_ids": ["pds_A"]
      }
    ]
  }
}
```

This is a proposed structure; the current manifest contract still needs extending to accept it.

Embedding it means one configuration describes both the vertical workflow and document links; the downside is that frequent inventory updates also change the configuration file. At the current scale of a few dozen documents, **embedding is reasonable**.

`inventory` should store provenance such as paths, hashes, roles, dates, and links; extracted results such as coverage amounts belong in extraction artifacts. At runtime, read only document entries relevant to the current task.

My current preferred direction is: **one main workflow, unified `item_schema`, document inventory embedded in the manifest, explicit amendment links, and shared quality checks using structure, evidence, and a judge.** No code changed and no merge was performed yet.
