**Recommended direction**
Build a 'multi-round Patch-Based Schema Refinement Pipeline.'

The core principle is: **The model does not directly rewrite the production schema. This is much more reliable than 'running the model a few more times to generate schemas directly,' because a production schema needs traceability, repeatability, and explainability.

#### Production Schema Refinement Pipeline

##### Problem Statement
How might we turn noisy one-shot LLM schema discovery into a stable, repeatable, auditable production schema refinement workflow for private health insurance extraction?

##### Recommended Direction

The system then normalizes field names/groups, counts field frequency across runs, applies decision thresholds, and automatically generates `refined_schema.yaml`.

- Human review UI — report files are enough for now.
- Database-backed schema registry — premature for this repo size.

##### Open Questions

- Should patch evidence include document quotes, page numbers, or just PDF paths for MVP?
- Should field decisions be configurable via CLI thresholds later?

Loop engineering can be understood as: **Designing not just a one-time generation step, but a closed-loop system of 'generate -> measure -> feedback -> regenerate.'**

It focuses not on 'did the model give me a seemingly good answer this time,' but on:

```text
1. Generate：生成 schema / extraction / result
2. Evaluate：用真实或 holdout 数据评价它
3. Diagnose：找出失败模式
4. Feedback：把失败变成下一轮可执行指令
5. Iterate：再跑一轮
6. Track：记录成本、质量、稳定性变化
```

So the core of loop engineering is: **The system can expose problems itself and convert them into signals for improvement in the next round.**

**Loop characteristics of the testing branch**
`testing` has a loop, but it is more of a **schema consensus loop**:


`holdout evaluation` means: **Do not evaluate the schema using the PDFs that generated it; test it with another batch of PDFs that did not participate in generation.**

If a schema was generated from batch A of PDFs, good performance on batch A does not mean it generalizes well. It may merely 'fit these samples.' So batch B of PDFs should be used as a holdout set.

In the current `feat/eval-cost-stability`, the logic is roughly:

```text
Discovery sample:
  用 seed=42 抽一批 PDFs
  -> 生成 schema

Holdout / evaluation sample:
  用 eval-seed=7 抽另一批 PDFs
  -> 用刚生成的 schema 去做 extraction
  -> 分析 extraction 失败在哪里
```

The corresponding command is:

```bash
python src/refine/loop.py --seed 42 --eval-seed 7
```

Here:

- `--seed 42`: used for schema discovery
- `--eval-seed 7`: used for holdout evaluation
- Different seeds aim to ensure the evaluation PDFs are not exactly the same as the schema generation PDFs

**What is a 'task-performance evaluation loop'?**
It means evaluating not just whether the schema file 'looks good,' but whether it 'works' in the actual downstream task.

Your downstream task is extraction:

```text
PDF + schema -> structured JSON record
```

So the task-performance evaluation loop is:

```text
1. Generate
   从 discovery PDFs 生成 schema

2. Execute Task
   用这个 schema 去抽取 holdout PDFs

3. Evaluate
   检查 extraction 结果：
   - 哪些字段总是抽不出来？
   - required 字段是不是经常缺失？
   - enum 字段有没有抽出 schema 允许范围外的值？
   - 有没有 PDF 抽取失败？
   - 模型有没有报告 _unfilled？

4. Diagnose
   把这些失败转成问题：
   - 字段描述太模糊？
   - 字段不该 required？
   - enum values 太窄？
   - schema 包含了 PDF 很少出现的字段？

5. Feedback
   生成 feedback.txt

6. Iterate
   下一轮 schema discovery 把 feedback 喂回去，让模型改进 schema
```

This is the closed loop:

```text
schema -> extraction -> failure analysis -> feedback -> improved schema
```

**Why this is stronger than looking only at the schema**
If you look only at the schema, you can only ask:

```text
这个字段名稳定吗？
这个 YAML 结构完整吗？
字段是不是很多？
```

But task-performance evaluation asks:

```text
这个字段真的抽得出来吗？
这个 required 字段真的每个产品都有吗？
这个 enum 列表够不够覆盖真实 PDF？
这个 schema 能不能帮助 extraction 产出可用 JSON？
```

This is closer to a production system, because end users ultimately want stable extraction results, not a beautiful schema.

**A concrete example**
Suppose the generated schema contains:

```yaml
- name: loyalty_bonus
  required: false
```

The schema itself looks fine.

But holdout extraction reveals:

```text
loyalty_bonus fill rate = 0%
```

This means it is barely extractable from the test PDFs. The system adds it to the feedback:

```text
loyalty_bonus was extractable in fewer than 25% of documents.
Either drop it, split it, or clarify its description.
```

When generating the schema in the next round, this feedback enters the prompt, and the model may:

- Delete `loyalty_bonus`
- Change it to a more accurate field
- Downgrade it to notes/optional
- Change the description to make extraction easier

This is what 'task-performance level' means: **Whether a field is retained depends not just on sounding reasonable, but on passing the extraction task.**

**Difference from the testing branch**
The `testing` branch is more like:

```text
字段在多轮 schema generation 里出现得频繁吗？
```

`feat/eval-cost-stability` is more like:

```text
字段在真实 extraction 里抽得出来吗？
```

Both matter, but the latter is closer to final system quality.

```text
PDFs
  -> generate baseline schema
  -> refine schema

       -> consensus: 多次 patch voting，让字段更稳定
       -> optional human review
```

**The actual current business main line**

The first step is **Generate schema**.

That is:

```text
PDF sample
  -> OpenAI
  -> schema.yaml
```

The entry point is:

```bash
python src/run.py
```

It does something straightforward:

1. Samples PDFs by category from `data/private_health/raw/PDFs/`.
2. Uploads PDFs to OpenAI.
3. Has the model generate a YAML schema.
4. Writes it to `outputs/private_health/schema.yaml`.
5. Logs token usage.

The goal of this stage is: **Obtain a usable baseline schema**.

The second step is **Refine schema**.

The entry point is:

```bash
python src/refine/loop.py
```

Refine is not another entirely separate product; it improves the quality of the schema generated in step one. It contains several actions:

```text
current schema / previous feedback
  -> generate schema draft
  -> consensus voting
  -> optional human review
  -> extraction evaluation
  -> feedback
```

The core goal is: **Make the schema more stable, easier to extract with, and more suitable for a production extraction pipeline.**

**What exactly consensus does**

Consensus is not a third business line. It is a stabilization step within refine.

Why is it necessary? Because the LLM may propose different fields each time it reads PDFs:

```text
run 1: annual_limit
run 2: yearly_limit
run 3: annual_benefit_limit
```

These may actually be the same field. Relying on a single generation allows schema drift. Consensus does the following:

```text
同一个 base schema
  -> 跑 N 次 patch generation
  -> normalize 字段名 / group 名
  -> 统计每个字段出现了几次
  -> 判断字段是 core / conditional / candidate / noise
```

So consensus answers:

> Is this field consistently considered by the model to belong in the schema?

It does not evaluate extraction performance directly. It evaluates **schema field stability**.

Actual task performance is evaluated by subsequent extraction evaluation:

```text
schema
  -> extract holdout PDFs
  -> analyze fill rate / required missing / enum violations
  -> feedback.txt
```

So their relationship is:

```text
consensus = 内部稳定性：字段多次出现吗？
evaluation = 外部有效性：字段真的能从 PDF 抽出来吗？
```

**Why there seem to be so many subpoints now**

Some internal steps have independently runnable CLIs for easier debugging:

```text
src/refine/consensus.py      单独跑 consensus
src/refine/review.py apply   单独应用人工审核结果
src/stability/compare.py     离线比较 schema drift
src/cost/estimate.py         单独估算成本
src/extract/analyze.py       单独分析 extraction JSON
```

```text
- consensus 是 refine 内部的字段稳定化步骤

- stability / cost / analyze 是辅助工具，不是主业务
```
