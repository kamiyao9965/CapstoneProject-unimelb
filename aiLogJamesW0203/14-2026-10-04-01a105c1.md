The version below can directly replace **4.4–4.9**. It retains original technical meaning and numbers with more direct wording. The original is from :codex-file-citation{path="/Users/yangyajing/Library/CloudStorage/OneDrive-TheUniversityofMelbourne/UoM/MAST90107/draft_v3.docx" purpose="source"}.

###### 4.4 Multi-Run Consensus

The model may suggest different fields each time it runs. To see which suggestions are consistent, we ask it to review the same draft schema several times using samples that can be reproduced. It can suggest adding fields, changing descriptions, or renaming, merging and moving fields. Minor spelling differences are normalised before voting, although fields with similar meanings may still be counted separately.

A field’s support is the percentage of runs that propose it. We group proposals into four levels: core at 80% or above, conditional from 50% to below 80%, candidate from 20% to below 50%, and noise below 20%. The most common suggestions determine the proposed data type and which products the field applies to.

High support does not automatically mean that a change is safe. An addition or description update must also meet the rules in the vertical’s manifest, have a complete definition, and have no rejection or conflicting definition. Protected identity fields cannot change automatically.

For example, a field proposed in four out of five runs has 80% support and enters the core group. It can still be blocked if a run rejects it or proposes a conflicting definition. Rejecting a proposed change leaves the existing field unchanged.

###### 4.5 Schema Human Review

Reviewers can accept, edit or reject proposed changes. Changes without a decision remain unapplied. The operator console normally pauses for this review. Command-line users can request the same step with `--review-ui`. If review is skipped, the system applies only changes that meet the automatic rules in the manifest.

Each review is linked to a specific proposal queue, schema version and insurance category. The system checks that the original schema has not changed, applies the accepted decisions, and saves the result as `reviewed_schema.json`. When a run resumes, it rebuilds this result and stops if the saved inputs no longer match. Reviewers can reject rename, merge and move proposals in the interface, but accepting these changes currently requires editing the base schema directly.

Review focuses on whether fields are clearly defined, duplicated, or relevant to the intended products. For example, a reviewer may clarify whether a baggage field means the total baggage limit or the limit for one item. This improves the extraction instructions, but it does not confirm that an amount extracted later is correct. Extracted values need their own checks against the source document.

Approving a Canonical Schema is a separate human decision. This approval is required before final quality auditing, CSV export and the supported database operations.

###### 4.6 Canonical Schema

Schema discovery produces a draft list of fields. The Canonical Schema is the version reviewed and approved for use. It defines what each field means, whether it is required, whether it can contain `null`, and where its value should go in the output. It also describes nested information and separates product details from information shared across the whole document. Extraction, quality auditing and export use these same definitions.

The system builds a Canonical candidate using local rules, without calling a model or writing to a database. It reuses known mappings where possible. For example, `product_name` maps to the shared product identity field. A simple baggage limit may map to a numeric column, while detailed benefits and source evidence can remain structured JSON. PostgreSQL stores these details in JSONB, avoiding a separate database column for every possible benefit.

Once the mapping is approved, loading and export follow it directly. They do not ask a model to decide where each value belongs. Changes to an approved contract require another review.

Travel’s earlier 29-field contract remains a reference for field mappings. New extraction runs need a contract that explicitly defines the allowed fields at every nested level, followed by a separately reviewed Canonical version. Similarly, Car’s 37-field v6 candidate is a starting point for review; future schemas do not have to contain exactly 37 fields.

PostgreSQL and CSV use the same approved mappings and record IDs. The CSV combines product identity, version, details and source information into one row per product release. Nested details remain JSON text within a cell. A vertical can therefore export CSV without enabling PostgreSQL storage.

###### 4.7 Extraction and Validation

The system converts the approved field definitions into JSON Schema, which specifies the structure of the extraction result. All four insurance categories return a `products` array, even when a document contains only one product. The result must include all declared keys, and it can use `null` only where the contract allows it. Extra keys are rejected, including those inside nested objects.

The output can also include `_notes` and `_unfilled` to explain missing product information. Information shared across the policy can be stored separately in `document_fields`.

The model provider receives the output rules, and local code checks the response again. These checks look for duplicate keys, invalid numbers, incorrect data types, unexpected structures, fields used for the wrong product type, and duplicate product identities. Missing amounts remain `null` where allowed. For discovered fields, `null` may also mean that the field does not apply to the product. `_unfilled` identifies relevant information that could not be found.

If a response fails validation, the system sends back the field name and the rule it broke, without repeating the problematic value. It allows up to two repair attempts. A refusal or empty response stops the process immediately. The system records the failure reason and usage for every attempt. Results that still fail are kept out of analysis and storage.

These checks confirm that the result follows the rules, but they cannot confirm every fact. For example, text in a numeric field may fail validation, while an incorrect amount written as a valid number may pass. A repair can fix the reported format problem without proving that the amount matches the PDF. Source-based review is therefore still needed.

###### 4.8 Quality Audit

After Canonical approval, all four insurance categories can use an optional model-based quality check, called LLM-as-a-Judge. The judge compares the extracted values with the approved field definitions and the page-numbered text from all PDFs in the source group.

Before this call, the system checks that the extraction, schema, insurance category and source PDFs belong together. It rejects inputs exceeding 120,000 source-text characters or 60,000 JSON characters, rather than cutting off part of the input.

The judge returns `pass`, `review` or `uncertain`. It also rates correctness, supporting evidence and uncertainty, and can report up to 25 findings. Each finding identifies the product, field and reason, with a source page and quotation where available. A pass requires no findings, satisfactory correctness and evidence ratings, and low uncertainty. A review result must include findings. Invalid source references trigger a repair attempt, while quotations that do not match the source need human inspection.

Human reviewers check every finding, every uncertain result, and a reproducible 5% sample of passes, rounded up to at least one. They record whether there is an issue, no issue, or continuing uncertainty. They can also record errors the judge missed. The review record uses file hashes to identify the exact inputs and settings, including pass results outside the sample, so later changes can be detected.

CSV export requires either a current judge pass or explicit human approval linked to the extraction, approved schema and complete source group. Recording ordinary review decisions does not approve delivery. The audit does not change extracted values or rerun extraction, and PostgreSQL loading follows its own validation rules.

The judge can make mistakes, particularly when it uses the same model or incomplete parsed text as the extractor. A high pass rate is therefore not an accuracy measurement. Human checks and independently labelled data are needed to measure how often the extracted values are correct.

###### 4.9 Method Selection and Alternatives

We use a shared schema so that equivalent benefits can be compared across insurers. Creating a separate structure for every PDF could produce fields with different meanings. Writing the entire schema by hand would require detailed knowledge of each insurance category in advance. Our approach uses discovery to suggest fields and human review to decide which definitions are suitable for use.

We extract from locally parsed Markdown because it is easy to inspect and can be used with different model providers. Sending PDFs directly to a model may preserve visual information that text parsing loses. Splitting documents or selecting passages could reduce token use, but it could also leave out related conditions or exclusions. Using the full parsed document avoids choosing passages in advance, although it requires larger prompts. We have not run a controlled comparison, so we cannot claim that this approach is more accurate.

PDFingestor is the default parser because it is simpler to set up. MinerU provides another option for investigating difficult layouts, but it requires additional pipeline models. Both produce the same parsed format for the rest of the workflow. Small development trials informed this choice, but they do not establish that either parser is more accurate.

We use repeated runs because one run cannot show how much the model’s suggestions vary. Voting identifies recurring suggestions, while review allows less common benefits to receive attention. Stricter voting thresholds can remove useful fields, as shown in Section 7.3. Travel uses five runs by default as a practical setting; this has not been shown to be the best number for every insurance category. Weighting votes by confidence remains experimental because the confidence scores have not yet been calibrated.

Local validation catches rule violations that model instructions and provider restrictions may miss. Allowing two repairs gives the model a chance to correct reported problems while limiting repeated calls. Validation checks structure, while source review checks the facts. Human review and sampling of judge passes remain necessary because the judge can also overlook errors.

For Travel, PostgreSQL stores products and versions in related tables, with JSONB for details that vary between products. CSV gives all four insurance categories an output that the team or client can open in Excel without a database connection. It uses the approved mappings and shared IDs, and retains nested JSON and source records. However, a flat CSV cannot fully represent every database relationship or distinction between values. The delivery approval step adds a final check before export.
