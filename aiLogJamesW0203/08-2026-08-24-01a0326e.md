### [2026-08-24T06:25:46.440Z] Codex

This project is fundamentally an experimental/governance pipeline for “automatically discovering and iteratively refining extraction Schemas,” rather than simply “batch-extracting PDF data.”

###### Overall logic

```text
分类后的保险 PDF 语料
        ↓
均衡抽样 + 内容去重
        ↓
LLM 发现一份通用 Schema
        ↓
可选：多轮 Patch 投票 + 人工审核
        ↓
把 Schema 编译成运行时抽取合同
        ↓
在未参与建模的 holdout PDF 上抽取
        ↓
分析填充率、缺失、分类错误
        ↓
生成 refinement_feedback.json
        ↓
人工或自动进入下一轮
```

###### 1. Schema discovery

The entry point is [src/run.py](/Users/yangyajing/Library/CloudStorage/OneDrive-TheUniversityofMelbourne/UoM/MAST90106/proj/CapstoneProject-unimelb/src/run.py:41).

It does the following:

1. Samples evenly from four PDF categories: `hospital / extras / generalhealth / combined`.
2. Selects different insurers within each category where possible.
3. Deduplicates by SHA-256 content hash, so the same PDF copied to different paths still counts as one document: [sampler.py](/Users/yangyajing/Library/CloudStorage/OneDrive-TheUniversityofMelbourne/UoM/MAST90106/proj/CapstoneProject-unimelb/src/schema/sampler.py:24).
4. Gives the model PDFs or Markdown converted by MinerU.
5. Asks the model to generate a Schema containing fields, product types, hospital categories, Extras services, and so on.

The Schema is not arbitrary JSON; it must pass all of:

- Strict JSON parsing;
- JSON Schema contract validation;
- Private-health business-rule validation;
- At most two repair retries.

This is concentrated in [discovery.py](/Users/yangyajing/Library/CloudStorage/OneDrive-TheUniversityofMelbourne/UoM/MAST90106/proj/CapstoneProject-unimelb/src/schema/discovery.py:117) and [structured_output.py](/Users/yangyajing/Library/CloudStorage/OneDrive-TheUniversityofMelbourne/UoM/MAST90106/proj/CapstoneProject-unimelb/src/common/structured_output.py:52).

It supports OpenAI, Anthropic, and DeepSeek; business code does not branch directly by provider, instead using [model_provider.py](/Users/yangyajing/Library/CloudStorage/OneDrive-TheUniversityofMelbourne/UoM/MAST90106/proj/CapstoneProject-unimelb/src/common/model_provider.py:84). DeepSeek accepts Markdown input only.

###### 2. Refinement main loop

The apparent entry point is `src/refine/loop.py`, but it is only a compatibility wrapper; actual orchestration is in [pipeline/rounds.py](/Users/yangyajing/Library/CloudStorage/OneDrive-TheUniversityofMelbourne/UoM/MAST90106/proj/CapstoneProject-unimelb/src/refine/pipeline/rounds.py:25).

Each round performs:

```text
生成 schema_draft
  → 可选 consensus
  → 得到 round_N/schema.json
  → holdout 抽取
  → 分析失败
  → 生成反馈
```

With `--consensus-runs > 1`, the model generates multiple Patch sets against the base Schema instead of rewriting the whole Schema repeatedly: [consensus.py](/Users/yangyajing/Library/CloudStorage/OneDrive-TheUniversityofMelbourne/UoM/MAST90106/proj/CapstoneProject-unimelb/src/refine/consensus.py:67).

Patches undergo alias normalization first, then are classified by occurrence frequency:

- ≥80%: core
- ≥50%: conditional
- ≥20%: candidate
- Lower: noise

Only safe core/conditional operations may merge automatically; reject votes, mixed operations, or rename/merge/move actions trigger human review. The review queue is immutable, with decisions stored separately in `review_decisions.json`; pending/reject items are not applied.

###### 3. Holdout extraction and evaluation

The final Schema compiles into runtime JSON Schema: [contract.py](/Users/yangyajing/Library/CloudStorage/OneDrive-TheUniversityofMelbourne/UoM/MAST90106/proj/CapstoneProject-unimelb/src/extract/contract.py:11).

An important detail: every field's JSON key must exist, but values not found may be `null`; the model must also return:

- `_unfilled`: fields it cannot fill;
- `_notes`: explanations of ambiguities.

Holdout excludes PDFs used in initial discovery or any consensus run, by content hash, preventing leakage.

Evaluation is in [analyze.py](/Users/yangyajing/Library/CloudStorage/OneDrive-TheUniversityofMelbourne/UoM/MAST90106/proj/CapstoneProject-unimelb/src/extract/analyze.py:152), focusing on:

- Applicable document counts and fill rates per field;
- Whether optional fields below 25% are weak fields;
- Missing required fields;
- Enum anomalies;
- `product_type` classification accuracy;
- The model's self-reported `_unfilled`.

Field applicability uses actual categories from PDF paths rather than predicted `product_type` to determine denominators. This avoids having the model “predict categories, then grade itself according to its own predictions.”

Analysis becomes `refinement_feedback.json`, appended to the Schema discovery prompt in the next round.

###### 4. Supporting tools

- Stability: generates Schemas repeatedly from the same fixed PDFs and measures model drift through set intersection-over-union.
- Cost: reads per-request JSONL token logs to estimate actual and projected costs.
- Vocabulary alignment: aligns hospital/extras names in Schema with labeled CSVs; this independent tool is not currently in the main loop.
- Artifact governance: all runtime artifacts have a standard envelope, provenance, and separate success/error handling; existing successful files are not overwritten by default: [json_artifacts.py](/Users/yangyajing/Library/CloudStorage/OneDrive-TheUniversityofMelbourne/UoM/MAST90106/proj/CapstoneProject-unimelb/src/common/json_artifacts.py:94).

### [2026-08-24T08:35:15.214Z] Codex

The project is fundamentally a pipeline platform for “insurance PDFs → reusable data structures → structured data → database.”

It does not parse PDFs using hardcoded fields or train models; the core idea is to have the model discover a Schema first, then use strict contracts to constrain subsequent extraction.

##### Overall data flow

```text
保险公司 PDF
   │
   ├─ Travel：先从官网发现并安全下载
   │
   ▼
PDF 预处理
   │
   ▼
LLM 发现字段结构
   │
   ▼
Discovered Schema（候选 Schema）
   │
   ├─ Private Health：稳定性、共识、人工审核、Holdout 评估、迭代
   │
   └─ Travel：直接提取，或人工批准为 Canonical Schema
   │
   ▼
根据 Schema 提取每份 PDF
   │
   ▼
经过 JSON Schema 和业务规则验证的 JSON
   │
   ├─ 评估、错误分析、成本统计
   └─ Travel：写入 PostgreSQL
```

##### Two business lines

| Capability | Private Health | Travel Insurance |
|---|---:|---:|
| Official-site PDF acquisition | Not currently supported | Supported |
| Schema Discovery | Supported | Supported |
| Single/batch extraction | Supported | Supported |
| Schema Refinement | Supported | Not currently supported |
| Ground Truth Evaluation | Supported | Not currently supported |
| Canonical Schema / PostgreSQL | Not yet enabled | Supported |

In other words:

- Private Health focuses more on “Schema research and iteration”: discovering fields from many existing PDFs and repeatedly evaluating schema stability and field extractability.
- Travel is closer to “complete business implementation”: acquiring insurer documents, discovering a Schema, extracting multiple products, manually approving a Schema, and writing to PostgreSQL.

##### Six main stages

###### 1. Official Travel document acquisition

```bash
python src/run.py crawl
```

Handled by `src/scraper/`:

- Discover links on configured official insurer websites
- Check domains, HTTPS, redirects, and robots.txt
- Download PDS, SPDS, TMD, FSG, and Brochure
- Verify files really are PDFs
- Save by SHA-256 to avoid duplicates
- Record products, document versions, and relationships

Raw PDFs go to:

```text
data/travel_insurance/raw/PDFs/
```

This stage makes no LLM calls.

###### 2. Schema Discovery

```bash
python src/run.py discover --manifest <manifest>
```

The flow is:

```text
分类抽样 PDF
→ PDFingestor 转换成阅读顺序文本和 Markdown 表格
→ 发送给 OpenAI / Anthropic / DeepSeek
→ 得到候选 Schema
→ JSON Schema 验证
→ 业务规则验证
→ 保存 discovered schema
```

Private Health categories are:

```text
hospital
extras
generalhealth
combined
```

Travel currently mainly uses PDS documents and identifies:

```text
international_single_trip
international_multi_trip
domestic
inbound
business
cruise
```

###### 3. Schema Refinement

Currently used mainly for Private Health:

```text
初始 Schema
→ 多次生成 Candidate Patch
→ 字段标准化和投票
→ Consensus Schema
→ 人工接受/拒绝/编辑
→ 用未见过的 Holdout PDF 测试
→ 生成 refinement_feedback.json
→ 下一轮优化
```

An important principle here: field applicability is determined by the real category of the PDF's directory, not the model's predicted `product_type`, so classification errors do not contaminate fill-rate statistics.

###### 4. Schema Application / Extraction

```bash
python src/run.py extract
python src/run.py batch
```

The candidate Schema is compiled into runtime JSON Schema, and the model must return results strictly following it.

The two business lines have different output granularity:

- Private Health: usually one PDF corresponds to one product record.
- Travel: one PDS may describe multiple Plans, so it returns a `products` array; Comprehensive, Basic, Domestic, and similar products cannot be merged into one record.

Returned model data is validated locally again. Failures allow at most two repair requests; if all three attempts fail, an error record is generated and invalid data cannot continue downstream.

###### 5. Evaluation

Private Health can use:

```bash
python src/run.py batch --evaluate
```

To compare extraction results with labeled data and calculate:

- Field accuracy
- Field fill rates
- Missing required fields
- Out-of-range enums
- Product classification accuracy
- Ground Truth matches
- Extraction failure counts

Schema stability also repeats discovery on the same PDFs to observe field-structure drift.

###### 6. Canonical Schema and PostgreSQL

Model-discovered Schemas are only candidates and cannot directly determine database structures.

The formal Travel flow is:

```text
Discovered Schema
→ 人工检查字段含义、类型、required、identity、存储策略
→ 标记为 approved
→ Canonical Schema
→ 编译 Extraction Contract
→ 生成 PostgreSQL DDL
→ 初始化数据库
→ 原子化写入提取结果
```

Corresponding command:

```bash
python src/run.py canonical-compile
python src/run.py storage-init
python src/run.py storage-load
```

The database uses:

- Fixed core tables for documents, runs, schema versions, etc.
- Extension tables per insurance vertical
- JSONB for flexible data
- Deterministic IDs preventing duplicates on reimport
- Full transaction rollback if any validation step fails

| Voting result | Automatic handling |
|---|---|
| 5/5 or 4/5, with consistent types | Accept automatically |
| 3/5 | Send to human review |

- Field types
- Enum values
- Applicable product types
- Requiredness recommendations
- Field descriptions

Yes, and the project is well suited to it. But I recommend putting LLM-as-a-judge in **offline quality evaluation after extraction**: it helps identify errors and prioritize human review, without directly approving Schemas, changing extracted values, or determining eligibility for database loading.

**What does eval usually mean?** Simply put, it means repeatedly testing a system with a fixed set of cases: give it the same inputs, record outputs, score them against explicit criteria, and compare quality, cost, and latency across models, prompts, or Schema versions. LLM-as-a-judge is just one kind of “grader,” not the entirety of eval. Graders can also be programmatic rules or human review. Both [OpenAI's evaluation guide](https://developers.openai.com/api/docs/guides/evaluation-best-practices) and [Anthropic's practical overview](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) use this combined approach.

**How does LLM-as-a-judge work?** Give the judge model the result being evaluated, clear grading rules, and verifiable evidence, and ask for structured judgments item by item. In this project, for example, evaluating a Travel product's “total baggage cover” should take the extracted value, field definition, corresponding PDS text and page number as input, and may output “supported by the source / contradicted by the source / insufficient evidence,” with supporting reasons. To compare two extraction versions, version names can be hidden and the judge asked to choose A, B, or a tie. Industry practice also calibrates judges against human annotations because judges exhibit position bias and a preference for lengthy answers; their scores cannot be treated directly as ground truth. [OpenAI's methods](https://developers.openai.com/api/docs/guides/evaluation-best-practices), [Google's judge calibration documentation](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/models/evaluate-judge-model), and [related research](https://arxiv.org/abs/2306.05685) all emphasize these limitations.

**How do others actually perform eval?** A common combination is offline regression on manually curated cases before release; sampled monitoring of new cases during operation; code-based checks for things code can determine (JSON validity, amount formats, required fields, etc.); judge-assisted assessment of semantic fidelity to the source; and human review for calibration and disputes. [LangSmith's evaluation documentation](https://docs.langchain.com/langsmith/evaluation-types) distinguishes offline comparison from online monitoring; [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) likewise explicitly separates code-, model-, and human-based graders.

For this project, the current state is clear: [Private Health already has label-based field metrics](/Users/yangyajing/proj/CapstoneProject-unimelb/src/evaluation/metrics.py:229); [Travel evaluation remains disabled](/Users/yangyajing/proj/CapstoneProject-unimelb/configs/travel_insurance/manifest.json:9) because there is no corresponding human-labeled dataset yet. Travel's five proposal votes measure **whether Schema suggestions are stable**, not whether PDF extraction is correct; all five can agree and all five can be wrong. The [project's fixes document](/Users/yangyajing/proj/CapstoneProject-unimelb/docs/fix.md:80) already proposes an offline teacher-model judge, but has not implemented it as an evaluation capability.

I recommend implementing in this order: first manually verify a small set of Travel samples spanning insurers, product tiers, and key fields; then add deterministic checks for amounts, product attribution, missing values, and so on; then let the judge **compare each product and field against original PDF evidence** to assess factual support; finally measure agreement with human conclusions, especially the proportion of “incorrect content judged correct.” Low-scoring or insufficient-evidence items enter human review, with judge results saved separately from raw extractions and database records. Crucially, evidence written by the extraction model itself is insufficient; the judge must be able to verify it against the PDF, and checking “what was omitted” requires a fuller source scope or human reference answers.
